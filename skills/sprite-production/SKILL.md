# Sprite Production

Produce a reproducible animation package whose drawings, motion, timing, metadata and target-engine playback pass explicit checks. A successful image-generation call, valid atlas or passing playback test alone does not make art production-ready.

Follow the user's art direction, asset scope, reference lineage and existing approval rules. Use the project's engine, exporter and viewer when present. Frame counts, camera angles and tolerances are decisions to derive, not universal defaults. Preserve original reference and generated bytes; version repairs. Resume from the last verified stage rather than regenerate accepted work.

## Work record

Keep a production checklist with the current stage, authoritative inputs, outputs, verification evidence and unresolved defects. Separate `planned`, `candidate`, `verified` and `approved` status. Record assumptions and their effect. Preserve existing reviews and ordering. A candidate becomes approved only through the project's stated approval process.

Use exact file paths and hashes in the reference register. A filename or a prose description is not a substitute for supplying the actual reference image to a drawing tool. Identify each image as identity, style, environment-scale, pose control or explicit edit target. Never promote a failed iteration to design authority.

## Ten stages

### 1. Define the production contract

**Inputs:** user request, current character art, style references, gameplay view, engine/import settings and current asset files.
**Do:** inspect those files and immediate consumers. Record direction convention, projection, target display sizes, sampling, handedness, gear, palette, canvas, origin, motion ownership and quality budgets. Resolve conflicting constraints before drawing.
**Output:** `production-contract.md` and a reference register with hashes, roles and selection evidence.
**Pass:** every decision needed for a pilot is explicit; unknowns are labeled and cannot silently become approvals. Read [planning and motion](references/planning-and-motion.md).

### 2. Define the asset and transition inventory

**Inputs:** contract, implemented character behavior and authorized planned behavior.
**Do:** build the action × direction matrix. For each clip specify purpose, entry condition, loop/one-shot/terminal behavior, support contacts, duration, events, cancel/recovery rule and equipment variants. Derive actual coverage; do not add invented mechanics to fill rows.
**Output:** inventory, transition table and estimated drawing/page counts, with required versus optional rows.
**Pass:** no required direction, action, held state or handoff is missing or represented by the wrong motion.

### 3. Establish canonical views and registration

**Inputs:** exact selected character, contract and inventory.
**Do:** define one logical canvas and a ground root separate from either foot. Mark proportion bounds, hips, knees, ankles, sole/heel/toe, hands and gear attachment points. Establish front/profile/rear visibility and occlusion for each required direction. Normalize only the whole source view/page; never scale individual poses by silhouette height.
**Output:** canonical view drawings/diagrams, anchor map and orientation/gear checks.
**Pass:** scale, camera, anatomical sides and the target engine's coordinate convention agree. Do not mirror asymmetric equipment unless the contract explicitly allows it.

### 4. Compute exact motion targets

**Inputs:** canonical anchors, clip inventory, required travel/stride, durations and error budgets.
**Do:** calculate every frame's phase, duration, root path, support identities, landmark coordinates, limb lengths, gear paths and depth order. Derive sampling from permitted temporal error. Include loop seams and input handoffs. Use code for coordinates and deterministic projection.
**Output:** machine-readable pose targets, per-frame tables and visible pose guides with stable frame identifiers.
**Pass:** planted contacts remain at their world targets, lift/travel is correct, limbs remain reachable and the cycle closes. Planned targets prove the plan only; they are not measurements of finished art.

### 5. Verify motion blocking

**Inputs:** computed targets and gameplay movement policy.
**Do:** play simple 2D skeletons or silhouette blocking at the intended scale, over stationary ground marks. Test the moving-root view as well as the in-place view. Check turns, arbitrary-phase stops, attacks, interruptions and recovery. Fix geometry/timing here before spending on detailed drawings.
**Output:** blocking playback, contact checks and a corrected pose plan.
**Pass:** motion is readable and contact-consistent; responsive input is not delayed to accommodate a convenient art loop. Read [authoring and repair](references/authoring-and-repair.md).

### 6. Draw and measure a pilot

**Inputs:** exact identity/style/scene references, one facing/action's targets, pose guide and self-contained drawing request.
**Do:** choose the smallest pilot that exposes the main risks, including a difficult view and idle when relevant. Supply actual images and embed the numerical frame table. Request one action/facing or manageable contiguous pose set. Preserve raw output, request, tool/version/settings and reference hashes. Register it to the canonical canvas, annotate actual visible landmarks and measure it.
**Output:** original pilot drawings, source registration, measured landmarks and a defect report with frame IDs.
**Pass:** real drawings satisfy geometry, identity, texture and scale checks. Static screenshots cannot prove motion. Follow the available image-generation tool/skill for raster authoring; do not replace requested character art with code-drawn stand-ins.

### 7. Repair failures, then complete coverage

**Inputs:** measured pilot, precise defect list, authoritative references and pose targets.
**Do:** repair the smallest failed frame range without altering accepted poses. Name one change per request and repeat invariants. Recheck every affected boundary. After the pilot passes and any existing approval gate is met, produce the remaining inventory in bounded units and measure each unit before promotion.
**Output:** versioned source frames, updated coverage matrix, measured checks and repair records.
**Pass:** required coverage is complete and no unresolved production defect is hidden. After two targeted attempts at the same failure, diagnose the method; do not keep buying identical free-form results. Switch to controlled 2D parts/rigging or explicit manual correction within authorization, or report the concrete capability limit.

### 8. Build the engine package deterministically

**Inputs:** verified source frames, canonical placements and target-engine/export contract.
**Do:** extract frame regions, retain canvas size and trim offsets, preserve pivots, then pack with compatible padding/extrusion. Export exact timing, direction, loop/hold, event and source mapping data. Check actual transparency, clipping, bleed, page limits and memory. Use the existing exporter or a known packing tool; image generation must not pack the final atlas.
**Output:** lossless alpha atlas pages, engine-readable metadata/resources, editable/original sources and reproducible export command.
**Pass:** every logical pose reconstructs at its original location and time; packed sampling introduces no neighbor pixels or edge artifacts. Read [export and playback](references/export-and-playback.md).

### 9. Validate the exported package in playback

**Inputs:** actual exported pages/resources, engine movement/animation clocks and acceptance budgets.
**Do:** load the export, not a separate demonstration copy. Inspect all clips/directions at intended and reduced size, normal and slow speed, contrasting backgrounds and actual filtering. Test delayed updates, loop seams, repeats, releases, turns, holds, interruptions and terminal poses. Measure contacts using actual runtime root travel. Exercise input control and named sequences when the task calls for a character tester.
**Output:** playback evidence, automated timing/contact checks and a frame-specific visual review.
**Pass:** rendering, travel, animation, input and metadata agree. A contact-test pass does not certify costume, anatomy, texture or appeal.

### 10. Deliver and mark the result accurately

**Inputs:** complete coverage matrix, source/export package, review decisions and stage evidence.
**Do:** run the finish checklist in the export reference. Report what changed, exact output paths, verification and remaining limits. Request only reviews required by the user's workflow. Follow repository checkpoint/commit instructions throughout; do not defer all commits until delivery.
**Output:** production package and completed production record, or a clearly labeled partial/study package with precise open defects.
**Pass:** call it production-ready only when required coverage, numerical checks, visual checks, engine checks and existing approvals all pass. If any required check was skipped or failed, say which one.
