Architecture decision and delivery plan

Dias Irae

A small, single-player isometric action role-playing game built with Godot and statically typed GDScript.

Status: accepted Version: 0.1 Updated: 16 August 2026

1. Context and goals

Force statement. Gameplay rules will change rapidly while combat feel is discovered; deterministic rules must remain testable without rendering or input; success is verified by a stable, enjoyable one-room vertical slice before scope expands.

This is a personal desktop game, not a live service. It has no networking, external database, compatibility burden, or team-scale deployment needs. The design therefore optimizes for correctness, fast iteration, readability, and clean gameplay boundaries—not theoretical scale.

Initial product goal

The player can move around one room, attack one enemy, take damage, defeat that enemy, die, and restart. Every later phase must preserve this playable loop.

Non-goals

  • Multiplayer, accounts, telemetry, cloud services, mod support, or console certification.
  • A generalized game framework or editor tooling before the game requires it.
  • Procedural worlds, crafting, skill trees, or generated loot in the first vertical slice.

2. Architectural position

The project uses lightweight domain-driven design (DDD) and applies the SOLID principles—single responsibility, open/closed, Liskov substitution, interface segregation, and dependency inversion—with judgment. Domain boundaries and invariants are strict; pattern ceremony is not.

Domain first

Code lives with the gameplay concept it owns. A domain contains its rules, state, Godot adapters, and tests.

Composition first

Scenes compose focused nodes and resources. Inheritance normally stops at the closest useful Godot type.

Explicit dependencies

Dependencies arrive through constructors or typed exported references. Mutable global singletons are prohibited.

Evidence before optimization

GDScript remains the default. Native extensions are considered only after profiling identifies a measured hotspot.

Inventory and equipment contract

The backpack is a 10 × 4 spatial grid. Every item has an authored rectangular footprint and may be placed only when every occupied cell is inside the grid and free. Items are not rotated.

Equippable items declare their allowed locations: head, chest, neck, left held hand, right held hand, covered hands, left ring finger, right ring finger, back, waist, legs, or feet. Rings may support either finger; one-handed items may support either held hand; two-handed items reserve both held-hand locations. Equipping removes an item from the backpack and unequipping requires enough free grid space.

4. Dependency rules

  1. Core combat state and calculations do not depend on input, animation, sound, user interface, or scene paths.
  2. Godot nodes adapt physics, areas, timers, and animation to typed domain operations.
  3. Synchronous rules use direct typed calls. Signals are reserved for one-to-many notifications such as “combatant defeated.”
  4. Cross-domain orchestration goes from service to service. A domain never reaches into another domain's internal node tree or state.
  5. The composition root assembles the initial scene and dependencies. Autoloads are allowed only for a proven application-lifetime concern.
  6. No Variant, untyped array, or untyped dictionary crosses a domain boundary.

6. Coding and testing standards

  • Use statically typed GDScript for properties, parameters, return values, arrays, and dictionaries.
  • Use Resource for authored immutable definitions and focused runtime objects for mutable state.
  • Keep _physics_process, input callbacks, and animation callbacks thin; they translate engine events into domain calls.
  • Names explain intent. Comments explain only non-obvious reasons.
  • Each business invariant receives a deterministic unit test. Scene tests verify wiring, collision, and lifecycle behavior.
  • Pin Godot and the selected GDScript test runner to compatible versions during Phase 0. Tests must run headlessly before gameplay implementation begins.
  • Profile before optimizing. A language or architecture change requires a recorded measurement and a repeatable benchmark.

7. Multi-phased implementation plan

Phase 0 — Foundation

Complete · 16 August 2026

Scope: Pin the Godot version; create the project and input map; establish typed GDScript warnings, formatting conventions, the test runner, headless checks, a main scene, and placeholder visuals.

Exit: A clean checkout opens without errors, tests run from the command line, and a placeholder character moves in an empty room.

Phase 1 — Combat vertical slice

Complete · 16 August 2026

Scope: Implement health and hit invariants, player movement, one attack, one pursuing enemy, damage feedback, defeat, player death, and restart. Use only placeholder art.

Exit: The initial product goal is playable for repeated runs; combat rules have unit tests; the scene has no errors or orphaned dependencies.

Phase 2 — Room loop and loot

Complete · 16 August 2026

Scope: Add several authored rooms, encounter completion, room transitions, one item type, pickups, a minimal inventory, and one meaningful equipment choice.

Exit: A player can clear a short sequence of rooms, receive a drop, equip it, and observe a tested combat change.

Phase 3 — Build depth

Meaningful variation

Scope: Add two complementary abilities, three enemy roles, a boss, upgrade choices, and save/load only if persistent runs are now valuable.

Exit: A complete run presents distinct tactical decisions and ends in a boss victory or player defeat; persistence round-trips exactly if implemented.

Phase 4 — Presentation and hardening

Personal release

Scope: Replace placeholders selectively; add sound, effects, camera polish, accessibility settings, performance profiling, balancing, export configuration, and regression checks.

Exit: The game exports and launches on the target desktop, completes a full run without errors, maintains the chosen frame-rate target, and has no known progress-blocking defect.

8. Decision gates

  • Do not begin a later phase until the current phase's exit criteria pass.
  • Do not add a domain, abstraction, or plugin without a current use case.
  • Do not add save-file compatibility until the game is distributed and real saves need preservation.
  • Do not introduce C++ or another language until profiling proves typed GDScript is the limiting factor.
  • Any persistent data contract is documented before code depends on it.
This document is the architectural baseline. Update it when a decision changes a domain boundary, dependency rule, delivery phase, or persistence contract—not for ordinary implementation detail.
